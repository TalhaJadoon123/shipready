## 1. Access control (CC6)

### CC6.1 Logical access

Access is granted on the principle of least privilege and reviewed at
<<ACCESS_REVIEW_PERIOD>>.

| Layer | Control |
| --- | --- |
| Identity | Single sign-on with mandatory MFA <<MFA_STATUS>> |
| Authorisation | Role-based access; routes enforce authorisation server-side, not in the client |
| Secrets | Stored in a secret manager; never in source, never in environment files |
| Offboarding | Access revoked within <<OFFBOARDING_SLA>> of an offboarding event |

### CC6.2 Credential lifecycle

Passwords are hashed with a memory-hard KDF (Argon2id or bcrypt). Reset flows
issue single-use, short-lived tokens. No password or full card number is ever
requested by an inbound phone call.

## 3. Change management (CC8)

### CC8.1 Changes are authorised

<<SOC2_CHANGE_MANAGEMENT>>

| Requirement | Implementation |
| --- | --- |
| Peer review | Required on every change; enforced by the platform, not convention |
| Automated checks | Lint, typecheck, tests, and a production-readiness gate |
| Separation of duties | The author cannot approve their own change |
| Emergency changes | <<EMERGENCY_CHANGE_PROCESS>> |

### CC8.1 AI-generated code

AI-assisted changes follow the same review path as any other change. A diff
produced by a model is reviewed like a diff produced by a person, and the
reviewer is accountable for it. Production readiness checks run identically.
